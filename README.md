# IKEA Dirigera Hub Integration for Home Assistant

[![HACS](https://img.shields.io/badge/HACS-Custom-orange.svg)](https://github.com/hacs/integration)
[![Version](https://img.shields.io/github/v/release/nrbrt/dirigera_platform)](https://github.com/nrbrt/dirigera_platform/releases)


A Home Assistant integration for the IKEA Dirigera hub, built on the [dirigera](https://github.com/Leggin/dirigera) Python library (v1.6.1). Originally forked from [sanjoyg/dirigera_platform](https://github.com/sanjoyg/dirigera_platform) and now under **active development**, with a strong focus on reliability : application-level WebSocket keepalive, automatic state re-sync on reconnect, and dynamic device discovery. Alongside broad device support and regular fixes. The most recent work lands in the [changelog](#changelog) below; issues are actively triaged.

Contributions are welcome, feel free to open [issues](https://github.com/nrbrt/dirigera_platform/issues) or submit pull requests. Device data dumps are especially helpful for adding support for new devices ([how to dump](docs/dump-data.md)).

## Highlights

- **Dynamic Device Discovery** : devices added, renamed, or moved to a different room in the IKEA Home app are automatically reflected in Home Assistant without a restart. Devices removed from the hub are detected; for now they are only logged (dry run, [#68](https://github.com/nrbrt/dirigera_platform/issues/68)), removal follows in a later release
- **Split-Device Merging** : newer IKEA devices (GRILLPLATS, TOFSMYGGA, TIMMERFLOTTE, MYGGSPRAY) expose as multiple API devices linked by `relationId`; the integration automatically merges them into one Home Assistant device
- **Real-Time Updates** : WebSocket events for lights, outlets, sensors, blinds, air purifiers, remote button presses and remote battery levels. Nothing but the air purifier polls (throttled); instead, a safety net re-reads the hub every 5 minutes, so an event the hub never sent does not leave a stale state behind
- **Lights switched together end where you asked** : commands go to the hub one at a time, one request per light, so an area or a scene no longer leaves bulbs on the wrong level or colour temperature; a bulb turned on from off with a brightness ends on that brightness
- **Your names and areas stay yours** : a name or area you set in Home Assistant is not reset to the IKEA name or room at a restart; the area only follows the IKEA app when the room changes there ([#72](https://github.com/nrbrt/dirigera_platform/issues/72)). Scenes follow the app too: renamed, new, and unavailable when the hub no longer lists them
- **Device sets as in the IKEA app** : import a set as one light, the set with its lights, or only the lights (see [Options](#options))
- **Resilient Connection** : application-level WebSocket keepalive reduces hub "inactivity" disconnects, and all device state is automatically re-synced on every reconnect, so entities never silently go stale after the hub drops the connection
- **Reliable Startup** : automatic retry on connection failure (`ConfigEntryNotReady`) instead of requiring manual reloads
- **Selective Import** : choose which platforms this integration sets up. If another integration such as Matter already covers your lights and plugs, import only what it does not, and the entities and devices of a deselected platform are hidden rather than left behind as unavailable ghosts
- **Multiple Hubs** : run more than one Dirigera hub side by side. Add the integration once per hub; each hub keeps its own device registry and event connection, so reloading one never disturbs another

### Not addressed (out of scope or different root cause)

- [#143](https://github.com/sanjoyg/dirigera_platform/issues/143), *Power factor for Inspelning*: the Dirigera API does not expose `currentPowerFactor`; would require a user-configurable correction factor + derived sensor, not a code fix.
- [#177](https://github.com/sanjoyg/dirigera_platform/issues/177), *STYRBAR 4 buttons*: the hub reports all four STYRBAR buttons as button 1, so the integration cannot tell them apart. This is a hub limitation.
- [#194](https://github.com/sanjoyg/dirigera_platform/issues/194), *TIMMERFLOTTE*: the two halves are merged into one device since v0.2.0, with a deterministic primary (name and room) since v0.3.26. Humidity stays at 1% precision: the hub sends `currentRH` as a whole number.
- [#153](https://github.com/sanjoyg/dirigera_platform/issues/153), *STARKVIND air quality*: the hub's PM2.5 value is exposed as a `Current pm25` sensor on the purifier, but without a STARKVIND we cannot confirm that it covers what the issue asks for. The purifier's state is pushed live since v0.4.1.
- Requests for devices the hub does not expose through its API (Matter device coverage, etc.) are out of scope for this fork's reliability focus.

## Requirements

- Tested on Home Assistant 2026.1 and newer (v0.2.6 and earlier work with HA 2024.12+)
- IKEA Dirigera hub on your local network
- HACS installed

## Installation

### Via HACS (recommended)

[![Open your Home Assistant instance and open a repository inside the Home Assistant Community Store.](https://my.home-assistant.io/badges/hacs_repository.svg)](https://my.home-assistant.io/redirect/hacs_repository/?owner=nrbrt&repository=dirigera_platform&category=integration)

Or manually:
1. In Home Assistant, go to **HACS** → **Integrations** → **⋮** (top right) → **Custom repositories**
2. Add `https://github.com/nrbrt/dirigera_platform` as an **Integration**
3. Search for "Dirigera" and install

### Update fails on Home Assistant 2026.11 or newer

If an update stops with *"The update could not be started: The dirigera_platform directory belongs to sanjoyg/dirigera_platform"*, the Marketplace (which replaced HACS in Home Assistant 2026.11) still has the original `sanjoyg/dirigera_platform` marked as installed next to this fork. This happens when you switched from the original to this fork under HACS. It is a known Home Assistant bug ([home-assistant/core#193096](https://github.com/home-assistant/core/issues/193096)), with a fix under review in [home-assistant/core#193106](https://github.com/home-assistant/core/pull/193106).

Until that fix is released:
1. Go to **Settings** → **Devices & Services**, open the **Marketplace** integration and **disable** it.
2. Make a copy of `/config/.storage/marketplace.repositories`.
3. In that file, find the block with `"full_name": "sanjoyg/dirigera_platform"` and remove only its `"installed": true` line. Leave the `nrbrt/dirigera_platform` block alone.
4. Save, enable the Marketplace again and retry the update.

Do **not** uninstall the sanjoyg entry from the Marketplace ("Delete and uninstall"): that removes your Dirigera setup together with all its devices and entities. See [#78](https://github.com/nrbrt/dirigera_platform/issues/78).

## Setup

1. Go to **Settings** → **Devices & Services** → **Add Integration** → search for **Dirigera**
2. Enter the IP address of your Dirigera hub (find it in your router's DHCP client list)
3. When prompted, press the **action button** on the Dirigera hub, then click Submit
4. Your devices will appear automatically

## Options

Open **Configure** on the integration to change these. Saving no longer asks you to press the hub's action button: as long as the hub address is unchanged and the stored token still works, the options are saved straight away.

| Option | Default | What it does |
|--------|---------|--------------|
| **Platforms to import** | all seven | Which device types get entities. Clearing a platform hides its existing entities and, where a device has nothing left, the device itself. They are disabled rather than deleted, so renames, area assignments and history survive; re-select the platform and they come back with the same entity IDs. A device that still has an entity on a selected platform stays visible, so switching off Sensors does not take a motion sensor or a metering plug with it. Anything you disabled by hand is never touched. |
| **Skip Matter over Thread devices** | off | Leaves out the devices the hub commissioned over Matter, for when you already import those through the Matter integration. Zigbee devices are unaffected. Devices imported for them before are removed at startup with their entities (since 0.4.1, [#75](https://github.com/nrbrt/dirigera_platform/issues/75)); turning the option off again brings them back as new devices. |
| **Importing sets of lights** | Sets only (new installs), Sets with lights (existing installs) | How lights in an IKEA device set are imported. **Sets only**: one light per set, as in the IKEA app; the lights in a set are not imported on their own. **Sets with lights**: the set, plus each of its lights. **Lights only**: no sets. Lights that are in no set are imported with every choice. |
| **Power sensor push throttle** | 60s | Minimum interval between recorder writes for the high-frequency push sensors. This is a floor, not an exact interval. Set 0 to disable. |

## Bug Reports & Feature Requests

When opening an issue, please attach a diagnostics file, it helps enormously:

1. Go to **Settings** → **Devices & services** → **IKEA Dirigera Hub Integration**
2. Open the three-dot menu next to your hub and choose **Download diagnostics**
3. Attach the file to the issue

Nothing is collected or sent by itself: the file is only made when you click. Your hub's address and token, serial numbers, coordinates, sun times, home/away state, Matter pairing codes and the names of your devices, rooms and groups are removed (the hub's time zone stays in); device ids are replaced by neutral ones (`device-07_3`) that keep their structure. Please look it over before you post it anyway.

The older `dirigera_platform.dump_data` service still works and writes the same anonymised list to the Home Assistant log (turn on debug logging for the integration first; with several hubs it dumps only one), see [detailed instructions](docs/dump-data.md).

### Recent

- **v0.4.1** (2026-11-27) First stable release of the 0.4 line: v0.4.0 and v0.4.1b1 to b4 together. One request per light and one command queue per hub ([#71](https://github.com/nrbrt/dirigera_platform/issues/71)), device set modes ([#73](https://github.com/nrbrt/dirigera_platform/issues/73)), names and areas you set in Home Assistant stay yours ([#72](https://github.com/nrbrt/dirigera_platform/issues/72)), Matter cleanup ([#75](https://github.com/nrbrt/dirigera_platform/issues/75)), less polling with a safety net every 5 minutes, and anonymised diagnostics. Next: one definition of a device for 0.5, see the RFC in [#77](https://github.com/nrbrt/dirigera_platform/issues/77).
- **v0.4.1b4** (2026-11-24, pre-release) A light turned on from off with a brightness gets the level in the same request and once more about a second later ([#71](https://github.com/nrbrt/dirigera_platform/issues/71), thanks @guaifi): bulbs that take it at once (KAJPLATS) no longer show their previous level first, and TRADFRI bulbs, which end part-way on the first request, end right after the second. Only a newer brightness or turning the light off cancels the second request. The first value a push sensor sends within a minute of the host booting is no longer delayed.
- **v0.4.1b3** (2026-11-18, pre-release) Less polling, and a safety net instead (upstream [#207](https://github.com/sanjoyg/dirigera_platform/issues/207), thanks @8871988-sketch): blinds and environment sensors get their state from the hub's events, and every 5 minutes one `GET /devices` and one `GET /scenes` per hub bring every entity back in line. Scenes follow the IKEA app (renamed, new; one the hub no longer lists becomes unavailable, it is not removed). Blind direction comes from the change in level, also for moves started with the remote. A command is no longer undone by an older state the integration was still reading from the hub.
- **v0.4.1b2** (2026-11-16, pre-release) The area of a device is yours, like its name ([#72](https://github.com/nrbrt/dirigera_platform/issues/72), thanks @AliBello): an area you deleted or chose in Home Assistant no longer comes back after a restart. The area follows the IKEA app only when a device's room changes there, also while Home Assistant is off; renaming a room takes along the devices still in the area named after it. Split devices (MYGGSPRAY) now always start in their room. The rooms last seen are kept per hub in Home Assistant's storage; the first start of this version only records them.
- **v0.4.1b1** (2026-11-16, pre-release) Commands to lights: one PATCH per light and one command at a time per hub ([#71](https://github.com/nrbrt/dirigera_platform/issues/71)); device sets send the command to each of their lights; a bulb turned on from off with a brightness gets the level about a second after it is on, so it ends on that level. Device sets: choose how they are imported (sets only, sets with lights, lights only; [#73](https://github.com/nrbrt/dirigera_platform/issues/73), PR [#76](https://github.com/nrbrt/dirigera_platform/pull/76) by @bjorncs), they follow the IKEA app while Home Assistant runs, and a set's state comes from all its lights. A name you gave a device in Home Assistant is no longer reset after a restart ([#72](https://github.com/nrbrt/dirigera_platform/issues/72)). With "Skip Matter over Thread devices" on, devices imported for Matter devices before are removed at startup ([#75](https://github.com/nrbrt/dirigera_platform/issues/75), thanks @owl70). Hub events are applied on Home Assistant's event loop. Diagnostics download with the hub's device list, anonymised.
- **v0.4.0** (2026-11-09, pre-release) Device events are applied through the entity's attribute model instead of a fixed list per device type, so remotes now update their battery level live (upstream [#167](https://github.com/sanjoyg/dirigera_platform/issues/167)) and air purifiers their state (upstream [#153](https://github.com/sanjoyg/dirigera_platform/issues/153)); values get their real type (datetimes, enums) and a value that does not fit keeps the old one. Another part of a split device (BILRESA, GRILLPLATS, MYGGSPRAY) may add values but no longer erases the battery level, the room or the name. Scene actions are only applied as state when the scene actually ran. The stale-device check (still a dry run, [#68](https://github.com/nrbrt/dirigera_platform/issues/68)) now also finds the empty per-half devices left by upstream, and keeps a device while it still has entities. Uses dirigera 1.6.1, which reuses one connection to the hub (PR [#74](https://github.com/nrbrt/dirigera_platform/pull/74) by @Leggin, part of [#71](https://github.com/nrbrt/dirigera_platform/issues/71)). The broken "mock" hub address is gone (upstream [#157](https://github.com/sanjoyg/dirigera_platform/issues/157)).
- **v0.3.29** (2026-10-26) Brightness is rounded instead of truncated between Home Assistant (0-255) and the hub (1-100). A scene setting brightness 158 used to come back as 155, and 140 as 137; a value that came from the hub now survives the round trip exactly, any other value is off by at most 1.
- **v0.3.28** (2026-10-26) Remote presses on buttons with a scene, follow-up to v0.3.24 (issue [#65](https://github.com/nrbrt/dirigera_platform/issues/65)). A trigger the hub sends without `triggeredAt` (a button or pattern never used yet) no longer fires; it used to fall back to the scene's `lastTriggered` and fire for a remote nobody pressed. A remote that sends `remotePressEvent` now uses only that for its presses, so a long hold no longer fires twice (the scene fires when the hold is recognised, `remotePressEvent` on release). The scene path stays for remotes without `remotePressEvent`. Thanks to @guaifi for the press matrix.
- **v0.3.27** (2026-10-26) Detect devices that are no longer on the hub, following Home Assistant's `stale-devices` rule. On every start and on each `deviceRemoved` event the integration compares its devices with the hub's full `/devices` list (unfiltered, so devices skipped by the Matter option or a deselected platform are never counted as gone). **This release is a dry run:** it removes nothing and logs a warning naming the devices it would remove. Nothing is done when the hub's list is empty or unusable, or when more than half of the devices would go. A device can now only be deleted by hand from its device page when the hub no longer has it.
- **v0.3.26** (2026-10-26) TIMMERFLOTTE: the two halves of a split environment sensor are merged into the same primary whatever order the hub lists them in (PR [#57](https://github.com/nrbrt/dirigera_platform/pull/57), upstream [#194](https://github.com/sanjoyg/dirigera_platform/issues/194)). The half with the temperature, the room and the `_1` suffix wins, so the sensor keeps the user's name and room and the refresh by `_1` works; the merge no longer writes into the hub's `/devices` response. On a hub that ever listed `_2` first, the entity's `unique_id` moves to `<rel>_1` and the old entity is left behind; delete it from the device page. Thanks to @jamesbiederbeck.
- **v0.3.25** (2026-10-26) Uses dirigera 1.6.0 instead of local model patches (PR [#67](https://github.com/nrbrt/dirigera_platform/pull/67)). The library now covers the light colour mode, motion sensors without `isOn`, controllers, colour temperature and stopping blinds, so `dirigera_lib_patch.py` shrinks by about 120 lines. Colour-temperature ranges reported in mireds (KAJPLATS) now show correctly in Home Assistant, and GRILLPLATS plugs whose metering half reports `type: "outlet"` no longer fail to load. Thanks to @Leggin, who maintains the library.

Both hub events now share one debounce on hub time, and the scene path uses each trigger's own `triggeredAt`. Thanks to @guaifi for the analysis and the captures.

- **v0.3.17** (2026-08-27) Choose which platforms to import (issue [#47](https://github.com/nrbrt/dirigera_platform/issues/47), upstream [#150](https://github.com/sanjoyg/dirigera_platform/issues/150)). Running Matter and Dirigera side by side gives you every device twice, because both integrations import the same hardware; scenes are the exception, since Matter does not sync them. A new "Platforms to import" multi-select decides which platforms this integration sets up, with everything selected by default so upgrading changes nothing until you touch it. Three things needed fixing underneath. Setup forwarded a hardcoded platform list while unload resolved that same constant, which drift apart as soon as the list depends on an option: a reload unloads first, and by then the new selection is already stored, so the platform you just switched off would never be unloaded and its entities would linger as orphans. Setup now stores the resolved list on the entry and unload reads it back. Not forwarding a platform also does not remove its entities: they stay in the registry as unavailable with `restored: true` and still show up in every entity picker, so they are now disabled instead. And disabling entities was not enough either, because Home Assistant keeps a device for as long as it has entities, so a filtered-out plug still sat in the device list next to its Matter twin; a device is now hidden too, but only when every one of its entities is on a deselected platform, so a motion sensor or a metering plug that spans two platforms stays put. Everything is disabled rather than deleted, which keeps renames, areas and history intact through a round trip. Saving options no longer re-runs the hub pairing: the options screen opens pre-filled and, when the address is unchanged and the stored token still answers, saves without asking for the action button. Verified on a live hub with 27 devices and 37 entities. Thanks to @Edocsyl for the report, for linking the upstream issue, and for testing it twice.

- **v0.3.16** (2026-08-23) Fix: a transient dip on the energy totals no longer inflates long-term statistics permanently (issue [#45](https://github.com/nrbrt/dirigera_platform/issues/45)). `total_energy_consumed` is a `TOTAL_INCREASING` sensor, so Home Assistant reads any decrease as a counter reset and adds the whole total to the statistics again. On a GRILLPLATS the value dipped from 5.982 kWh to 5 kWh for 137 ms after a hub reconnect and then corrected itself, which injected the full total three times in two weeks; on a plug sitting at 263 kWh one dip would inject 263 kWh. A decreasing `totalEnergyConsumed` or `energyConsumedAtLastReset` is now only written when the device also reports a newer `timeOfLastEnergyReset`, or when the value drops to zero, which is how a genuine reset is reported. As a safety valve, a lower value that persists for three consecutive updates is accepted anyway, so a reset the hub fails to timestamp can never freeze the sensor. Thanks to @0xmachos for tracing this all the way into the statistics table.
- **v0.3.15** (2026-08-09) Fix: the power sensor push throttle dropped the final value instead of deferring it (issue [#44](https://github.com/nrbrt/dirigera_platform/issues/44)). A push arriving inside the throttle window was discarded, which is harmless while pushes keep coming but not when the device goes quiet right after one: switching a plug off stopped the `electricalSensor` events, so the last value never reached Home Assistant and the off-clamp that forces the power sensors to 0 was never applied. Until v0.3.12 the HA poll masked this by writing the cached value anyway; v0.3.12 disabled that poll, so the regression window is v0.3.12 through v0.3.14. A throttled push now schedules a trailing write at the end of the window, so the final value always lands while the write rate stays capped. Thanks to @Cornitus for the screenshot that pinpointed it.
- **v0.3.14** (2026-07-11) Docs: clarify that the push throttle is a *minimum* interval, not an exact one (issue [#40](https://github.com/nrbrt/dirigera_platform/issues/40)). Because a write only happens when a device push actually arrives, the effective interval rounds up to the first push after the limit elapses. With a sensor that pushes every ~30s and a 60s setting, the second push (~59s) is still blocked and the third (~89s) clears it, so the real interval is about 90s. This is correct throttle semantics (a floor), so rather than change the behaviour the option now documents it in its help text. Thanks to @m3gg3 for the precise measurement (89.2s observed vs 89.1s predicted) on real ALPSTUGA hardware.
- **v0.3.13** (2026-07-11) Extend the push throttle to the environment sensors (issue [#40](https://github.com/nrbrt/dirigera_platform/issues/40)). Following v0.3.12, the VINDSTYRKA/ALPSTUGA temperature, humidity, current PM2.5, VOC index and CO2 sensors now also set `should_poll = False` and honour the throttle interval, since these values arrive over the WebSocket push (they are in the `environmentSensor` push allowlist) rather than needing the poll. The min/max measured PM2.5 sensors are the exception: those values are *not* pushed and only refresh on the poll fetch, so they keep polling (they change rarely, so their recorder footprint is negligible). The "Power sensor push throttle" option now governs these sensors too. Thanks to @m3gg3 for confirming from debug logs that ALPSTUGA push updates arrive independently of the poll cycle.
- **v0.3.12** (2026-07-11) Fix: the v0.3.10 power-sensor push throttle was silently bypassed by Home Assistant's own polling (issue [#40](https://github.com/nrbrt/dirigera_platform/issues/40), reopened). The current amps, active power and voltage sensors never overrode `should_poll`, so HA kept polling them on its default ~30s cycle and wrote the (already WebSocket-updated) value straight to the recorder, ignoring the configured throttle. Because these sensors' outlet device sets `skip_update=True` and they are driven entirely by the ~8s WebSocket push, that poll produced nothing but redundant recorder rows. They now set `should_poll = False`, so the throttled push is the only state-write path and the configured interval is actually honoured. Energy totals are unaffected. Thanks to @m3gg3 for catching the gap. Note: the environment sensors (VINDSTYRKA/ALPSTUGA) are poll-fetch driven rather than push driven, so they need a different approach, tracked in the issue discussion.
- **v0.3.11** (2026-07-09) Fix: stop the WebSocket listener from pushing HA state during shutdown once the event loop is closed (issue [#42](https://github.com/nrbrt/dirigera_platform/issues/42)). The listener runs on its own thread and keeps handling hub events for a few seconds after Home Assistant has already closed its asyncio loop; every event that reached `schedule_update_ha_state` in that window raised `RuntimeError: Event loop is closed` and was logged as a warning with a full traceback, once per incoming event. `on_message` now checks `_request_to_stop`/`loop.is_closed()` before scheduling the update, the same guard the keepalive path already used, so shutdown stays quiet. Normal operation is unchanged. Thanks to @m3gg3 for the precise root-cause analysis and the ready-made patch.
- **v0.3.10** (2026-07-01) Throttle HA state pushes for outlet power sensors (issue [#40](https://github.com/nrbrt/dirigera_platform/issues/40)). Smart plugs with power metering push `currentActivePower`/`currentAmps` over the WebSocket roughly every 8 seconds, so the current amps, active power and voltage sensors wrote about 10,800 recorder rows per day per entity. Each of those sensors now rate-limits its HA state push to a minimum interval (default 60s, cutting it to about 1,440 rows/day). The sensor's internal value is still updated on every push, so `native_value` keeps returning the live reading and only the recorder write is skipped. The interval is configurable in the integration options ("Power sensor push throttle"); set it to 0 to disable throttling. Energy totals (`total_energy_consumed`, `TOTAL_INCREASING`) are unaffected. Thanks to @m3gg3 for the detailed analysis and the ready-made patch.
- **v0.3.9** (2026-06-30) Fix: guard the device state-update cascade against listeners that were never added to Home Assistant (issue [#41](https://github.com/nrbrt/dirigera_platform/issues/41)). A device fans a hub push out to its sensor listeners via `schedule_update_ha_state`; a listener that was registered but never added to HA has `hass=None`, so HA dereferences `self.hass.loop` and raises `AttributeError`. That surfaced as a flood of "error processing hub event" warnings, typically on outlets and electrical sensors pushing power readings every few seconds. The cascade now skips listeners with no `hass`, which is behaviour-neutral since an entity not registered with HA cannot receive a push anyway.
- **v0.3.8** (2026-06-24) Fix: per-hub device registry (issue [#39](https://github.com/nrbrt/dirigera_platform/issues/39)). The device registry was a single shared dict and `stop()` cleared all of it, so with two hubs, unloading or reloading one config entry wiped the other hub's registrations too. After that, every event for the other hub's devices came in as an unknown device and its state was never applied, so those devices stopped updating entirely (not tied to one device type). The registry is now keyed per hub, so reloading one hub no longer affects another.
- **v0.3.7** (2026-06-24) Fix: re-sync all device state on WebSocket reconnect (issue [#39](https://github.com/nrbrt/dirigera_platform/issues/39)). Dirigera hubs drop the event WebSocket fairly often; on reconnect the integration only waited for new events and never re-pulled current state, so any change made during the disconnect gap was lost and entities silently went stale over time, affecting every device type, not just one. (A config reload worked around it because a reload re-fetches all state.) On reconnect the integration now fetches `/devices` once and replays each device through the normal update path, with discovery suppressed during the replay. No more manual reloads.
- **v0.3.6** (2026-06-24) Fix: stop the runtime re-discovery loop for devices without an entity (issue [#39](https://github.com/nrbrt/dirigera_platform/issues/39)).
